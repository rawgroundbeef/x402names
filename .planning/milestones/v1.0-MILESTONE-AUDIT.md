### Design Note: Payment Middleware

`createPaymentMiddleware` factory (Phase 2) is exported but not applied to routes. Routes use manual `decodePaymentSignatureHeader()` instead. This is an intentional architectural choice providing:
- Granular control over payment validation per endpoint
- Custom error messages
- Easier idempotency integration
- Not a broken integration — documented as valid trade-off

## E2E Flow Verification

### Flow 1: Domain Discovery — COMPLETE
```
GET /tlds → 30 TLDs with USDC pricing
POST /domains/check → availability + price
```

### Flow 2: Registration — COMPLETE
```
POST /domains/check → available
POST /domains/register (payment) → 202 Accepted + jobId
  → Background: registrar.register() → insert domains → DNS config → status='live'
GET /registrations/:jobId/status → succeeded + artifactUrl
```

### Flow 3: URL Update — COMPLETE
```
GET /domains/:name/status → ownerWallet confirmed
PATCH /domains/:name/url (payment) → updated
  → DB updated → cache invalidated → redirect serves new URL
```

### Flow 4: Error Handling — COMPLETE
```
Rate limit hit → 429 + Retry-After + RFC 9457
GET /errors → error catalog with 26 codes
Agent implements retry based on retryable flag
```

### Flow 5: DNS — COMPLETE
```
Domain registered → DNS auto-configured via registrar API
GET /domains/:name/dns → server IP + records + instructions
GET /domains/:name/dns/verify → propagation status
Redirect server serves domain → 301 to targetUrl
```

## Tech Debt Inventory

### Phase 1: Foundation (1 item)
1. **Railway config relative paths** — startCommand uses relative paths that would fail when Railway runs from repo root. Note in verification says this was fixed in commit 21ea585, but should be verified in deployment.

### Phase 4: Registration Flow (1 item)
1. **Payment signature verification** — `TODO [HARD-05]` in register.ts. Server-side x402 payment signature verification against facilitator not implemented. Current implementation decodes and validates payment amount, which is sufficient for v1 (facilitator handles settlement independently). Wallet address used for attribution only.

### Phase 5: URL Forwarding (1 item)
1. **ACME challenge placeholder** — redirect/server.ts has a placeholder route for ACME challenges that returns 404. SSL provisioning not implemented. Would be needed for HTTPS redirect serving.

### Phase 6: Production Hardening (2 items)
1. **Per-wallet rate limiting** — Only per-IP rate limiting implemented. Design decision: paid endpoints are naturally throttled by payment cost. Acceptable for v1 scale.
2. **Unused payment middleware factory** — `createPaymentMiddleware` in middleware.ts is exported but not used by any route. Routes use manual payment decoding instead. Could be removed or documented as reserved for future use.

### Cross-Cutting (2 items)
1. **Unused system table** — `system` table defined in schema but has no active consumers. Reserved for future metadata storage.
2. **Human verification items** — 4 items flagged in Phase 6 verification for manual testing: rate limiting under real load, URL validation IP edge cases, error catalog agent discovery UX, validation error aggregation end-to-end.

**Total: 7 tech debt items across 5 areas. 0 blockers.**
